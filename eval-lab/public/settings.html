Connect the MES database

This is all that is required for natural-language questions about the line. The platform connects straight to the UNICOMM database with a read-only pool — no connector process, no second repository, no bridge. Set six values, restart, verify.

◈
Read-only by construction. Questions are answered by generating a SELECT, and every statement passes a deny-by-default guard before it reaches the database: single statement only, SELECT/WITH only, no DDL or DML, no stored procedures, no SELECT … INTO, row cap and query timeout enforced. Sessions run READ UNCOMMITTED so a reporting query can never take locks that block the line's own writes.
1

Set the connection

On the plant LAN or WiFi, WARKFSQL002 resolves directly and no VPN is needed — the VPN section below is only for off-site development. Ask Comer IT for a read-only login; the guard enforces read-only regardless, but a least-privilege credential is the correct posture for a production MES.

backend/.env 
MES_MSSQL_HOST=WARKFSQL002        # ← MES SQL host — per site
MES_MSSQL_PORT=1433
MES_MSSQL_DATABASE=SSL04_FARGO    # ← line database — Rockford axle line
MES_MSSQL_USER=<READONLY_SQL_USER>       # ← read-only login from Comer IT
MES_MSSQL_PASSWORD=<READONLY_SQL_PASSWORD>
MES_STATION_NUMBER=100            # ← default station (ST100 · Pinion Guide)

Optional, with sensible defaults: MES_PLANT_TZ (America/Chicago — the timezone the MES writes its timestamps in), MES_MAX_ROWS (200), MES_QUERY_TIMEOUT_MS (15000), MES_SESSION_IDLE_MS (900000 — how long after the last phase a station still counts as working).

2

Verify

The health endpoint answers the only two questions that matter: can we reach the database, and is the plant moving? A configured-but-unreachable database returns 503, so this fails loudly instead of quietly serving demo data. The startup log prints the same verdict on every boot.

shell · verify 
curl -s localhost:3001/api/mes/health | jq
# → connected: true, newestPhaseAt: "2026-08-19 07:38:43", newestPhaseAge: "1 minute"

# what the assistant is allowed to see
curl -s localhost:3001/api/mes/schema | jq '.tables[].name'

# ask a question — the answer carries the SQL that produced it
curl -s -X POST localhost:3001/api/mes/ask -H 'Content-Type: application/json' \
  -d '{"query":"How many units did station 110 build today?","lang":"en"}' | jq
◈
Two things this database does not carry, both of which the assistant states plainly rather than guessing around. SSL_Users is empty, so operator identity is the badge number in Operator_ID — there are no names to look up. And there is no planned time, downtime or cost data, so OEE and scrap cost cannot be derived here; those live in the downtime system and ERP.
Reachability. The hosted platform runs outside the plant, so it cannot reach WARKFSQL002 on a private LAN address — putting your own laptop on the Comer network does not change what the hosted server can reach. For live line data on comer.theomnia.ai the database needs a route from outside (published host, tunnel, or Render dedicated outbound IPs allowlisted by Comer IT). To demo without that, run the platform locally on a machine that is on the plant network.

MCP server setup — UNICOMM line connector

Optional — not required for this platform. The live-line service uses the direct connection above. This connector is the separate path for exposing the same data to MCP-capable clients (Cursor, Claude Desktop, an internal agent runtime) as curated tools rather than SQL.

The connector is fed by a read-only Model Context Protocol server that sits next to the MES database and exposes a small set of curated tools — never raw SQL. This is the same connector developed for the Comer Rokid build (connectors/mssql-unicomm-database). Installing it on an on-site host is a 15-minute job for IT personnel with database and network access.

◈
Design guarantees. The connector opens the SQL connection with read-only intent, ships no write path, and exposes only curated tools (workstation snapshot, phase results, technician on task, measurement history, session state). Plant directors query it in natural language from this platform — no SQL knowledge required on the floor.
1

Prerequisites

An on-site host (VM or container) with Node.js 20+, a read-only SQL login on the line database, and network reach to the MES SQL host — at Rockford that is WARKFSQL002 / database SSL04_FARGO. If the host is off the plant network, set up VPN access first (next section).

shell · smoke-test connectivity 
# confirm the SQL host answers before installing anything
sqlcmd -S WARKFSQL002,1433 -d SSL04_FARGO -U <READONLY_SQL_USER> -Q "SELECT 1"

Install the connector

The connector lives on the connectors/mssql-unicomm-database branch of the Comer Rokid repository. Access to the repository is granted by Omnia per developer.

shell · install 
git clone https://github.com/AldoOmnia/comer-rokid-demo.git
cd comer-rokid-demo
git checkout connectors/mssql-unicomm-database
cd connectors/mssql-unicomm-database
npm install && npm run build

Configure the environment

All open values are flagged — host and database names are per-site and owned by Comer IT. Never commit this file. The UNCOMM_ prefix is spelled exactly as the connector reads it. On the plant WiFi/LAN WARKFSQL002 resolves directly, so no VPN is needed; the VPN below is only for off-site development.

.env 
BACKEND_API_KEY=<ROTATED_API_KEY>    # ← REQUIRED — guards /v1/unicomm/*; the process refuses to start without it

MES_ADAPTER=unicomm               # ← poll SSL04_FARGO instead of the mock adapter
UNCOMM_ENABLED=1
UNCOMM_MSSQL_HOST=WARKFSQL002     # ← MES SQL host — per site
UNCOMM_MSSQL_PORT=1433
UNCOMM_MSSQL_DATABASE=SSL04_FARGO # ← line database — Rockford axle line
UNCOMM_MSSQL_USER=<READONLY_SQL_USER>      # ← read-only login provisioned by Comer IT
UNCOMM_MSSQL_PASSWORD=<READONLY_SQL_PASSWORD>
UNCOMM_MSSQL_ENCRYPT=1
UNCOMM_MSSQL_TRUST_CERT=1
UNCOMM_READONLY=1
UNCOMM_STATION_NUMBER=100         # ← station in scope (ST100 · Pinion Guide)
UNCOMM_TEST_NUMBER=X900.SWR.901.A01

What the connector code looks like

A representative excerpt: a read-only connection pool and one curated tool. The full connector ships five tools shaped exactly like this — no free-form SQL surface.

src/connector.ts · sample 
import sql from "mssql";

// Read-only intent at the driver level — the connector has no write path.
const pool = new sql.ConnectionPool({
  server: process.env.UNCOMM_MSSQL_HOST!,        // WARKFSQL002
  database: process.env.UNCOMM_MSSQL_DATABASE!,  // SSL04_FARGO
  user: process.env.UNCOMM_MSSQL_USER,
  password: process.env.UNCOMM_MSSQL_PASSWORD,
  options: { encrypt: true, readOnlyIntent: true },
  pool: { max: 4 },
});

/** Curated tool: the live snapshot for one workstation. */
export async function fetchWorkstationSnapshot(stationNumber = 100) {
  const db = await pool.connect();
  const r = await db.request()
    .input("station", sql.Int, stationNumber)
    .query(/* parameterized TOP-1 snapshot query — station, step,
             technician, serial, latest measurements + verdicts */ QUERY);
  return r.recordset[0] ?? null;
}

Point this platform at the bridge

Once the connector's HTTPS façade (/v1/unicomm/health, /v1/unicomm/workstation) is reachable, set two environment variables on the platform deployment. The Live line card on the home page switches from demo data to live automatically — no UI work.

platform environment · Render 
LINE_BRIDGE_URL=https://<ON_SITE_BRIDGE_HOST>:8443   # ← the on-site connector façade
LINE_BRIDGE_API_KEY=<ROTATED_API_KEY>              # ← must equal the connector's BACKEND_API_KEY
The connector never leaves the plant network — this platform reaches it only through the authenticated HTTPS façade above. SQL credentials stay on the on-site host.
Reachability. The hosted platform runs outside the plant, so it cannot see WARKFSQL002 or a bridge on a private LAN address — putting your own laptop on the Comer network does not change what the server can reach. Live line on the hosted URL needs LINE_BRIDGE_URL to resolve from the public internet (published host or tunnel, API key enforced). To demo without that, run the platform locally on a machine that is on the plant network and point it at the bridge on localhost.

VPN access — Cisco

The MES SQL host is only reachable from the plant network. Comer's remote access runs on the Cisco stack (Secure Client / AnyConnect). Off-site connector hosts and developer workstations connect through it before anything in the MCP section will resolve.

▲
Open variables — confirm with Comer IT before rollout. These values are site- and provider-specific; the network provider can change and the gateway, group profile and DNS values move with it. Nothing below is hard-coded in the connector.
  • <VPN_GATEWAY> — the Cisco headend, e.g. vpn.comer-plant.example
  • <GROUP_PROFILE> — the tunnel group assigned to MES/engineering access
  • <AD_USERNAME> — the Active Directory account (MFA push follows)
  • <BRIDGE_HOST_IP> — the on-site host running the MCP connector
1

Interactive access — Cisco Secure Client

Developer workstations use the Secure Client UI or its CLI. Install from the Comer IT software portal, then:

shell · macOS / linux CLI 
# Cisco Secure Client CLI (macOS path shown; Windows: "Cisco Secure Client" app)
/opt/cisco/secureclient/bin/vpn connect <VPN_GATEWAY>
# → group: <GROUP_PROFILE> · user: <AD_USERNAME> · approve the MFA push
2

Headless access — connector host

For the unattended host that runs the MCP connector, openconnect speaks the AnyConnect protocol and runs cleanly under systemd:

shell · headless host 
sudo openconnect --protocol=anyconnect \
  --user=<AD_USERNAME> \
  --authgroup=<GROUP_PROFILE> \
  <VPN_GATEWAY>

Prefer a service account with a certificate profile over a personal AD login for anything unattended — request it from Comer IT.

3

Firewall / split-tunnel request

The connector needs exactly two flows. Submitting this as the firewall request keeps the access review simple:

access request · two rules 
# 1 — connector host to the MES SQL server (read-only login)
allow tcp <BRIDGE_HOST_IP> -> WARKFSQL002:1433

# 2 — platform egress to the connector's HTTPS façade
allow tcp <PLATFORM_EGRESS_IP> -> <BRIDGE_HOST_IP>:8443
4

Verify end-to-end

shell · through the tunnel 
# SQL reachability (expect one row: 1)
sqlcmd -S WARKFSQL002,1433 -d SSL04_FARGO -U <READONLY_SQL_USER> -Q "SELECT 1"

# connector façade health (expect JSON with "config")
curl -H "x-api-key: <ROTATED_API_KEY>" https://<BRIDGE_HOST_IP>:8443/v1/unicomm/health
Provider note: Comer runs Cisco today. If the network provider changes, only the gateway, group profile and client software in this section change — the MCP connector, the firewall rule shapes and the platform wiring above stay identical.
